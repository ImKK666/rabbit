## 一 · 动手前量出来的五个事实

不是估计，是读码 + 实跑得到的。**方案里每一条选择都挂在这五条上面。**

### ① `taskRegistry.cancel()` 只 abort 不 release —— 而且它自己知道

`runtime/taskRegistry.ts:99` 的注释原文：

> 代价是取消之后到任务真正收尾之间，这个键仍然是「占用中」，
> 用户此刻重发会收到「已有任务在执行中」。**这是对的** ——
> 上一轮的收尾写入（保存 deck、推送状态）还没跑完，
> 此时放新任务进来就是 BitFun 状态机里 `FINISHING` 要防的那件事。

那条注释是对的，但它描述的是一个**没有出口的正确**：用户点了停、立刻改口，
得到的是一句拒绝。排队输入要填的正是这个窟窿 —— 不是把闸门拆掉，
是在闸门外面放一个队列。

### ② 被拒的输入在面板上长得像被受理了

`src/store/agent.ts:103` 的 `submitTask` **先把用户那句 push 进 log，再 send**。
后端拒绝时回的是 `{type:'error'}`，前端 `case 'error'` 只追加一条红字，
**那句用户消息仍然留在日志里**，看起来像是发出去了。

而且 `case 'error'` 这条分支**不还画布所有权**（`submitTask` 在发出请求时
就已经 `setDeckOwner('agent')`）。所有权要等那个真正在跑的任务发出
`agent.status: done/error` 才还回来。

**所以这不只是缺一个功能，是一个现存的 bug。**

### ③ server 侧没有 playwright，`playwright-core` 是刻意不进依赖的

`server/package.json` 的依赖里没有任何浏览器。根目录的 `scripts/shoot-layout-sheet.mjs`
头注释写着 `npm i --no-save playwright-core   # 一次性，刻意不进 devDependencies`。

**「渲染后反思走后端无头」是一笔真实的新部署面**（chromium 及其一堆系统库），
不是顺手加个依赖。

### ④ 渲染后反思的判据和量法，`measure-layout-text.mjs` 已经写死了

那个文件的头注释是这一节最重要的输入：

> `design.ts` 的 `estimateTextHeight` 是**估**的……版式引擎拿这个估值往下累加 `y`，
> 决定下一个元素放哪。估小了，下一个元素就压上来。
> 而这件事**现有的检查一条都看不见**：
> - `Builder.text()` 会把框高夹进画布，所以 `lintSlide` 的「超出画布」永远不会响
> - 重叠检查比的是**声明的框**，而溢出发生在框**外面**（PPTist 不裁剪文本）
>
> 于是 66 张样张跑下来 **0 告警**，其中好几张我肉眼就能看到文字压在一起。

它给出的解法也已经验证过：**不问「框在哪」，问「字画到哪了」** ——
量 `.text` 节点的 `offsetHeight`，容差 4px，`offsetHeight` 不受祖先
CSS transform 影响所以缩放不用换算。

**这条事实有两个后果**：一是渲染后反思的第一档不该是「VLM 看截图」，
是把量出来的真实几何回灌；二是**负对照是现成的** ——
同一页今天跑 `lintDeck` 就是 0 告警。

### ⑤ FTS5 在 bun 里可用，但默认 tokenizer 对中文一个都搜不到

bun 自带 sqlite 3.51，FTS5 编译进去了。实跑：

| 建表 | 查询 | 命中 |
|---|---|---:|
| `fts5(body)`（默认 unicode61） | `设计系统` | **0** |
| `fts5(body)`（默认 unicode61） | `交付速度` | **0** |
| `fts5(body, tokenize='trigram')` | `交付速度` | 1 |
| `fts5(body, tokenize='trigram')` | `返工率` | 1 |
| `fts5(body, tokenize='trigram')` | `团队交付`（原文里不连续） | **0** |

语料是同一句：`设计系统能让团队的交付速度提升 40%，返工率下降一半`。

两个结论：**必须用 trigram**；**trigram 只认连续子串**，
「团队交付」这种跨词组合搜不到，所以查询词要么是连续短语，
要么由代码拆成 2~4 字 n-gram 再 OR。

**这条不实测就会做出一个「跑得通但永远搜不到」的东西** ——
建表成功、插入成功、查询成功、返回 0 行，全程没有任何东西报错。
和 12 号文档那条「对某类错误不敏感的判据等于没有判据」是同一族毛病。

## 二 · 排队输入（11 号文档 C 期）

### 队列放后端，不放前端

理由是事实 ①：队列必须跨过 FINISHING 窗口，而**只有后端知道那个窗口什么时候关**。
前端排队的话，它只能靠「有没有收到 done」猜，而 done 发出之后
`drain()` / `touchConversation` 还在跑。

### 形状

```
runtime/inputQueue.ts        域无关、不碰 bun:sqlite（所以 vitest 里测得到）
  按 WorkspaceKey 分队 · FIFO · 每队上限 3

orchestrator.runAgentTask
  acquire 失败 → enqueue + 回 agent.queued { position }
  finally 的 release 之后 → 取下一条接着跑
```

**接力必须在 `release` 之后，不能在 `drain` 之前。** 否则排队的输入
和上一轮的收尾写入抢跑，那正是 BitFun 的 `FINISHING` 要防的事（10 号文档 §1.5）。

### 三条容易漏的边

- **断线**：排队项持有 ws 引用，连接没了它的产出就没有观众。
  `taskRegistry.cancelAllMatching` 现在**一处调用都没有**（全仓只有定义和一处注释提到它），
  断线不取消任务这件事本来就欠着 —— 队列要和它一起补上
- **取消 = 全停**：`agent.cancel` 取消在跑的那一轮 **+ 清空该工作区的队列**，
  回执里说明丢了几条。心智上用户点「停」就是停，留着队列会出现
  「我明明停了它还在做」。这是一行的事，要改成保留很容易
- **前端不许再撒谎**（事实 ②）：`agent.queued` 到达时那条用户消息要标成
  「排队中（第 N 条）」，被拒时那条消息要能被标成「未发送」而不是静静留着

### 判据

| # | 判据 | 怎么判 | 负对照挂哪 | 状态 |
|---|---|---|---|---|
| Q1 | busy 时发第二句 → 队列长 1；第一轮结束后**自动开跑** | `taskGate.test.ts` + 端到端 | 把「release 后取下一条」注释掉 → **实测 10 条红** | ✅ |
| Q2 | 第二轮的 `messages` 含第一轮的全部工具调用 | 端到端数库里的行 | 12 号文档 §E 那条「接在同一个历史后面」 | ✅ |
| Q3 | 同一 workspace 任何时刻只有一个任务在跑 | 端到端数「同时在跑的峰值」 | 同 Q1 | ✅ 峰值 1 |
| Q4 | 取消 → 队列清空，且没有半条排队项漏跑 | `taskGate.test.ts` | — | ✅ |
| Q5 | ws 断开 → 该连接的排队项清掉，别的连接不受影响 | `taskGate.test.ts` | 把断线跳过去掉 → **实测 2 条红** | ✅ |
| Q6 | 队列满 → 明确拒绝并说明，不静默丢 | `inputQueue.test.ts` | 静默丢是这个仓库的典型失败模式 | ✅ |
| Q7 | 被拒 / 排队的输入在面板上**不许显示成已受理** | `inputDelivery.test.ts`（13 条） | 去掉 `delivery` 标记 → **实测 8 条红**（这就是那个现存 bug 的原版） | ✅ |

### 落地记录（2026-08-20）

**① 接线单独抽了一个文件 `runtime/taskGate.ts`，这是计划里没有的。**
原计划把「占坑 → 排队 → 接力」写在 `agent/orchestrator.ts` 里。写到一半发现
那个文件经 `pipeline.ts` → `db/index.ts` 拉 `bun:sqlite`，**vitest 里 import 不进来** ——
写在里面等于没有判据。而这段恰恰是 11 号文档 §五那条教训点名的地方：
**零件对 ≠ 装配对**（`taskRegistry` 和 `inputQueue` 各自全绿，接错线时一条都不响）。
`domains/deck/channel.ts` 当初拆出去是同一个理由。

**② 协议从两条消息收成一条带状态的。** 一开始设计的是
`agent.queued` + `agent.dequeued` 两种消息，写前端时发现**第三种情况没人管**：
队列满被拒的那句，前端仍然显示成已受理。收成
`agent.input { state: 'queued' | 'started' | 'rejected' }` 之后三种情况都有着落，
而且**每一句输入恰好收到一个终局回执** —— 前端的 FIFO 配对全靠这条对称性。

**③ 实测撞出两个真 bug，都是「不会报错」的那类：**

- **FIFO 配对要分状态找。** 只按「还没有终局回执」找的话：
  `A 已开跑 · B 排队中 · C 刚发出` 时，C 的 queued 回执会落在 B 上，
  C 永远停在 pending。由 `inputDelivery.test.ts` 的「同一句话连发两次」一条抓出来
- **`InputQueue.enqueue` 的上限检查被绕过了。** 「队列还不存在」那条分支
  直接塞进去，于是 `maxPerKey = 0`（配成「完全不排队」）时第一条照样进得来。
  由 `taskGate.test.ts` 的「被拒的那条只有 rejected」抓出来

**④ 断线只丢排队项，不取消正在跑的任务。** 原计划写的是「挂进 `cancelAllMatching`」，
实现时发现**不能这么做**：闸门按 `deck:<id>` 键登记，不记是哪个连接发起的，
同一份 deck 可能在另一个标签页里也开着，按连接取消会误杀。
而且任务的 deck 改动是落库的，用户刷新回来仍然拿得到 —— **断线不等于白跑**。

### 端到端实测（真后端、真 WebSocket、真模型 deepseek-v4-pro、真库，跑完即删）

```
连发两句 →  回执序列 started → queued → started
            同时在跑的峰值 1
            两轮落在同一条会话里（user 行 2 条）
            第二轮开跑前历史里已有 1 个 tool-call

第二轮问「刚才那个主色你是从哪个工具看到的」
       →  「getDesignTokens」    ← 一个工具都没调
```

最后那句是整件事的判据：排队进来的第二句**接在同一份历史后面**，
所以它不用重新查就知道上一轮做了什么。

规模：**约 1 轮**（实际用掉约 1 轮）。

## 三 · 渲染后反思（11 号文档 D3）

### 决策：前端量，不是后端无头

**已决策（2026-08-20，决策者选的）：走前端量。**

三条路的账：

| 路 | 依赖 | 量的是什么 | 判据性质 |
|---|---|---|---|
| **前端量（选中）** | 零 | 用户真正看到的那个渲染器 | 确定性，每次一样 |
| 后端无头 | playwright + chromium（事实 ③） | 服务端另起的一个渲染器 | 确定性 |
| VLM 看截图 | 视觉模型配置 | 模型的观感 | **每次不一样，当不了判据** |

### 决策修正：VLM 那一档也做，但必须是**独立配置的模型**

> **原文我写的是「VLM 这一版不做」。决策者当场纠正：
> 「反思渲染要搞一个工具，同时这个工具的模型要重新设置成一个独立的模型。」
> 这条修正是对的，原文保留 —— 我的理由只对了一半。**
>
> 我对的那一半：**几何测量绝不能过模型**。「declared vs actual 差几像素」是纯计算，
> 一过模型就从「每次结果一样」变成「每次不一样」，判据就没了。
> 12 号文档 §六② 定的方向在这一半上仍然成立。
>
> 我漏掉的那一半：**「看一眼这页丑不丑」本来就不是几何能回答的问题**，
> 而 12 号文档 §六② 明确记着丢掉的正是这两条 ——「空洞的套话」和
> 「该用图表却排成文字」。这两条既然要补回来，就只能靠模型。
>
> 而「必须独立配」是硬约束，不是偏好：**实际在用的 deepseek 没有视觉能力**，
> 用 deck agent 那个模型根本看不了图。配了个没视觉的模型比没配更糟 ——
> 请求发得出去、会返回一段一本正经的胡话，**而没有任何东西会报错**。

所以这一版的分工是：

| | 靠什么 | 每次结果 | 装配条件 |
|---|---|---|---|
| **几何测量** | 前端量 + 现有的 `lintSlide` | **一样** | 永远有 |
| **视觉复核** | `reflect` 角色的**独立视觉模型** | 不一样 | 配了、且 `supportsVision`（能读图）才有 |

> **实测追记（2026-08-20）：这一档配上去之后，第一次跑就撞出两个真 bug，
> 而且两个都属于「不会报错」的那类。它们比这一节的设计本身更值得记。**
>
> **① 我差点用错字段。** 原本打算复用 `modelConfigs.supportsImages` 当门禁，
> 写到一半查了它现在的用法 —— 它是**「能出图」**（`AssetSettings.vue` 拿它筛生图模型），
> 不是「能读图」。复用的后果是：给 `gemini-3.7-flash` 打上这个标之后，
> 它会出现在「生图用哪个模型」的下拉里，**而它一张图也生不出来**。
> 于是加了 `supports_vision` 一列（迁移 `0007`）。四种组合都真实存在：
>
> | 模型 | 出图 | 读图 |
> |---|---|---|
> | deepseek-v4-pro | ✗ | ✗ |
> | gemini-3.7-flash | ✗ | ✓ ← 视觉复核要的是这一档 |
> | gemini-3.1-flash-image | ✓ | ✓ |
>
> **② `normalizeBaseUrl` 对 google 的处理一直是坏的，只是没人撞到。**
> 库里配的中转是 `https://g.92.run/v`，路径非空，按原来那条
> 「已有路径的一律不动」原样交给 SDK，于是它 POST 到
> `…/v/models/gemini-3.7-flash:generateContent` —— **少了 `/v1beta`，每次 404**。
>
> 没被发现是因为：deck agent 配的是 deepseek，而生图那条路**根本没走 SDK**
> （`imageGenerate.googleImageEndpoint` 自己拼 URL，规则正好是对的）。
> **同一件事在两处有两套判断，一边能用一边 404。** 现在两处用同一条规则，
> 并且「规则一致」本身成了一条判据（`baseUrl.test.ts` 拿两个函数的输出对一次）。

**机制是现成的，仓库里早就留好了口子。** 12 号文档 §C 把 `AgentRole`
收窄成 `'deck'` 时明写着：「这一维刻意保留，删掉等于一个用户只能配一个模型，
而第二个域接进来时马上要按域配不同的模型」。这一版就是那一维第一次被用起来：

- `AGENT_ROLES` 加一个 `'reflect'` → 管理员的角色默认页和用户的模型偏好页
  **自动多出一档**（两处的 `z.enum` 都从这个列表取）
- 门禁照抄图片能力那条：没配 / 配的模型没勾「支持图片」→ **整档不做**，
  日志说清楚缺什么。R-32 的教训原文：「一个永远返回『未接入』的工具只会白白消耗步数预算」
- **视觉复核一个工具都不给**（`toolGroups.ts` 里 `reflect: []`）：
  它只出意见，动手的仍然只有 deck agent 一个 —— B 期「单一权威写者」那条不能破
- 它的 `maxSteps` 是 **1**：没有工具就没有第二步。写成 1 而不是随便给个大数，
  是让「它不该有多步」在代码里有个位置，哪天有人给它加了工具，这个 1 会立刻报出来

### 形状

```
agent 调 reflectRender(slideIds?)
  → 后端 channel 发 agent.render.request { requestId, slideIds, wantShots }
  → 前端离屏渲染（复用 ThumbnailSlide → BaseTextElement，和
     scripts/layout-sheet.ts 走的是同一条路，没有第二实现）
     量每个文本元素：declared（元素声明的 height） vs actual（.text 的 offsetHeight）
     wantShots 时顺便 html-to-image 截一张（这个依赖树里已经有了）
  → agent.render.result 回来
  → 几何：贴回真实高度，重跑 lintSlide，**减去原本就有的那些**
  → 视觉：每页一次独立视觉模型（最多 6 页，超出的部分明说）
  → 一起返回给 agent
```

**离屏靠位移（`left:-2000px; opacity:0`），不靠 `display:none`。**
`display:none` 的节点根本不参与布局，`offsetHeight` 一律是 0 ——
而 0 的意思是「每块文字都画得下」，报告一片祥和。判据 R3 的负对照盯的就是这个。

**量到之后不写新的检查**：拿 actual 高度克隆出一份「测量后的 slide」，
直接跑现有的 `lintSlide` —— 重叠 / 越界 / 安全区那套几何检查一行不用重写，
换的只是输入。这是事实 ④ 里那句「溢出发生在框外面」的正面解法：
把框改成真实的框，原来的检查就看得见了。

### 这条路顺带建出 `agent.confirm` 等的那个机制

`ws/handler.ts:114` 那个空着的 `agent.confirm` 分支，注释写的是
「需要后续实现 agent 中途暂停等待机制」。`measureRendered` 要的正是同一个东西：
**后端发一个请求、挂起、等前端回一个带 requestId 的答复**。
一次投资两处收益，所以这个等待器放 `runtime/`，不放 deck 域。

### 唯一的新风险：阻塞

11 号文档风险表里那条「权限闸门带来新的交互面 —— 阻塞式确认在 WebSocket
断线时会死锁」，这一版第一次真的踩到它。

**硬要求：超时必须有，超时后降级成「这次没量到」，绝不挂起。**
agent 拿到「没量到」要能继续往下走，而不是卡在那儿。

| # | 判据 | 怎么判 | 负对照挂哪 | 状态 |

| R5 | 迟到的 / 伪造的 requestId 不会污染另一次测量 | `pendingRequests.test.ts` | `settle` 改成「找不到就随便挑一个」→ **实测红** | ✅ |

| V4 | 视觉调用全失败时**不许说「没挑出问题」** | 端到端（指向一个假模型名） | 就是实测撞到的那个 bug 的复现 | ✅ |

**判据 R3 换了个问法，值得记一笔。** 原计划是「和 `measure-layout-text.mjs` 量出来的一致」，
但那两个脚本量的**不是同一件事**：那个脚本量的是「版式引擎估得准不准」（declared vs actual），
而这里真正的风险是「离屏那条路可不可信」（onscreen vs offscreen）。
所以改成在同一个页面里把同一批页量两遍：一遍正常挂在文档流里，一遍走
`measureRenderedSlides`，逐个元素比。**公式仍然逐字相同**
（`declared = style.height`、`actual = .text 的 offsetHeight`、容差 4px）。

这个换法是被负对照逼出来的：把离屏容器改成 `display:none`，
`offsetHeight` **全部变成 0**，而 0 的意思是「每块文字都画得下」——
报告一片祥和，**没有任何东西会报错**。原来那个问法抓不住这种情况。

### 视觉复核实测（真 gemini-3.7-flash + 真截图）—— 以及我自己踩的那个坑

**第一次跑是假绿，记一笔，这是本轮最值得记的一次判据失效。**

第一版实测：库里那页是我在测试脚本里 `buildLayout` 造的 bullets，
而发给模型的截图是探针截的 **title-center** —— 两页根本不是同一页。
模型回「这几页没挑出问题」，我差点当成通过。

**而「它没看见图」和「它看了图觉得没问题」在报告里长得一模一样。**
更糟的是当时代码里这两件事**返回同一个值**：`reviewOne` 的 catch 分支
和「模型说无」都 `return null`，汇总成同一句「没挑出问题」。
翻服务端日志才看到 `AI_APICallError: Not Found` —— **每一次调用都 404**，
而工具报告一片祥和。这正是这一节开头警告过的那个失败模式，我自己踩上了。

两处都改了：

1. **截图和 slide JSON 由探针一次吐出**（`--shot-out` + `--slide-out`），
   「库里那页」和「模型看到的那张图」从此不可能对不上
2. **`reviewOne` 返回三态**（有意见 / 没问题 / 失败带原因）。全失败时
   工具明说「视觉复核**一页都没跑成**（N/N）：<原因>」，并单独回
   `visualReviewed` / `visualFailed` 两个数 —— 数字比一句话更难被读漏

修完之后的实测（探针 `--bad` 渲染一页故意写坏的稿子：套话 + 百分比排成文字）：

| # | 判据 | 结果 |
|---|---|---|
| V1 | 配了能读图的模型 → `wantShots=true` | ✅ |
| V2 | 工具返回里带上视觉复核意见 | ✅ |
| V2 | **正对照**：意见里出现页面上真有的内容 | ✅ 模型逐字引用了「全面赋能业务增长」「数据驱动」等标题 |
| V3 | 换成不能读图的模型 → `wantShots=false` | ✅ 不白截一次图 |
| V4 | **负对照**：每次调用都失败时不许说「没挑出问题」 | ✅ 明说「一页都没跑成（1/1）：Not Found（404：多半是 baseUrl 少了版本段…）」 |

**V2 那条正对照是这一组的核心** —— 光有「视觉复核」四个字不算数，

建议：将各项替换为具体的业务举措和量化成果
     （例如将"提升效率"改为"审批流自动化，单据处理时长缩短 40%"）。

问题：版面内容全部挤在左侧窄条区域，右侧大面积严重空置，视觉重心极度失衡。

第一条正是 12 号文档 §六② 砍掉 Reviewer 时明说「先丢掉」的那两条之一
（「空洞的套话」），现在被这一档接回来了。
**它没抓到另一条**（「该用图表却排成文字」—— 那三个季度百分比），
一次实测说明不了什么，但先记着。

## 五 · 摄入（11 号文档 D2 的后半）—— **TODO，尚未动手**

**验收标准由决策者定死了**：*「几乎所有材料都应该可以吃 ——
pdf / txt / 图片 / word 文档 / md / json / 网页 url 等都要能吃才对。」*

这和 [README 的一页速览](./README.md#一页速览) 里写的原始目标一致
（「喂给它现成的资料（PDF、Word、txt、图片、网页、参考 PPT）」），
不是新增需求，是那条一直欠着的。

### 查出来的地形

- **server 侧一无所有**：没有 zip、没有 pdf、没有 docx 的任何依赖，
  `routes/` 五个文件里**一处 `formData` / `multipart` 都没有**。后端摄入是从零开始
- **前端已经有 `jszip`**（还有 `pptxtojson` / `pptxgenjs`）。
  docx / xlsx / pptx 本质就是 zip + XML，**这个能力已经在树里了**
- `runtime/objectStore.ts` 是手写的 COS 客户端，内容寻址 put 已经跑通 ——
  原始文件存哪儿不用重新做

### 设计：按「解析在哪」分三档，不按格式分

```
第一档 · 浏览器侧解析（覆盖绝大多数格式）
  txt / md / json / csv        零依赖
  docx / xlsx / pptx           jszip 已在树里，解 zip 抽 XML 文本
  pdf                          pdfjs-dist（浏览器是它的主场，不是勉强跑）
  → 只把抽出来的文本传给后端；原文件按需进 COS

第二档 · 服务端解析
  网页 URL                     fetch + 正文提取
  ← 必须在后端：agent 自己也要能抓，调研那条路用的就是它

第三档 · 模型解析
  图片 / 扫描版 PDF            VLM 转文字
  ← modelConfigs.supportsImages 开关位已在 schema，
    门禁照抄 imageCapabilityAvailable()：没配视觉模型就明说这一档不可用
```

**解析放浏览器的理由，和渲染后反思选前端量是同一个**：那台浏览器本来就在，
能力也本来就在。顺带省掉三件事 —— server 不用扛 bun 上 pdf 库的兼容性风险、
几十 MB 的文件不用过后端、材料在被主动上传之前不离开用户自己的机器。

代价是**摄入必须有人在场**。可接受：摄入本来就是用户动作。
真正需要无人值守的是「agent 自己抓 URL」，而那一档在后端。

### 材料怎么进上下文 —— 这是最关键的一处

**绝不能把整篇正文塞进 tool result。** 一篇文章 5k~50k token，
而现在的上下文裁剪只有「从旧往新丢整轮」这一招（12 号文档 §A），
塞两篇就把历史挤没了。

形状是**落库 + 按需翻书**，和 Claude Code 的 Read/Grep 同一个形状。
**不做 embedding** —— 又一个 provider 依赖 + 又一个失败面：

```
materials(deckId, kind, title, url, text, chars, createdAt)
material_chunks + FTS5(tokenize='trigram')      ← 事实 ⑤，必须 trigram
  searchMaterial(query, k)   → top-k 片段 + materialId + 位置
  readMaterial(id, from, to) → 取指定范围
```

事实 ⑤ 要写进代码注释：trigram 只认连续子串，
所以工具描述里必须让 agent 用**连续短语**查询，或由代码把查询拆成
2~4 字 n-gram 后 OR。**先做最简单的一步，实测中文命中率，
不行退回 LIKE + 打分**（09 号风险表那条）。

### 一条硬规矩要先立

统一入口 `ingest(source) → Material`，按 MIME / 扩展名分发到一张 parser 表。
**不认识的格式必须明确报「不支持，因为 X」，绝不允许静默产出一份空材料。**

这条不是洁癖，是事实 ⑤ 的同族：一份空材料落进库，agent 会拿着它
「读」出一片空白，然后照样把稿子做完 —— 而**没有任何人会知道
那篇 PDF 其实一个字都没进去**。

### 判据

| # | 判据 | 负对照挂哪 |
|---|---|---|
| I1 | 每种格式一个 fixture，抽出的文本含一个已知片段 | 损坏 / 加密 / 空的样本 → **必须报错**，不许产出空材料 |
| I2 | 「字数为 0 的材料不许落库」这条不变式 | 把检查去掉 → 必红 |
| I3 | 扫描版 PDF（无文本层）→ 被识别出来并转第三档 | 最容易静默失败的一种：它会当成「一份 0 字的 PDF」 |
| I4 | 没配视觉模型时第三档明确不可用，且**说得出缺什么** | 照抄图片能力那条门禁 |
| I5 | 中文查询能命中中文材料 | 换回默认 tokenizer → 必须红（事实 ⑤：今天它静默返回 0 行） |
| I6 | 30 万字的材料摄入后，本轮请求体不因此增长 | 防「正文漏进上下文」—— 这件事不会报错，只会变贵变笨 |
| I7 | 每条被引用的材料能反查到 URL | 合规。图片那套的教训：**字段留了不等于兑现了** |

规模：**2~3 轮。**
