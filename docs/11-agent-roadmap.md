# 11 · Agent 强化路线：从「生成 PPT 的剧本」到通用 agent

**方向决策（2026-08-19）**：把 rabbit 的 agent 从「一段生成 PPT 的硬编码剧本」
强化成**通用 agent 系统**，PPT 是它的第一个域，不是它的全部。

依据的判断：**PPT 的天花板不在排版，在内容。**
现在每一份 deck 的内容来源只有「模型的内部知识 + 用户那几句话」——
调研是空的、摄入是空的、图片是空的。排得再漂亮，也是一份漂亮的空话。

研究依据见 [10-agent-runtime-study.md](./10-agent-runtime-study.md)（BitFun + Claude Code）。

---

## 一 · 先把「强大」定义准，否则会把已有成果吐回去

`08-expressiveness.md` 第九节用十二轮实测收敛出一句话：

> **模型被要求做的决策本身就不该由它做。**

而且这条是**有实测背书**的：`applyLayout` / `shapeCatalog` / `layouts.ts` 的出场编排，
每一样都是把决策从模型手里拿走之后质量才跳的。第十轮那 8 个错误版式，
也明确判过「主修在 `layouts.ts`，不在 Reviewer」。

所以「加强 agent」**不等于**「给模型更多自由」。精确的说法是：

| 维度 | 天花板在哪 | 该怎么加强 |
|---|---|---|
| 排版 / 配色 / 动画编排 | **已经靠代码化摸到了** | 继续往代码里挪，**不要还给模型** |
| 内容从哪来 | 完全空白 | 调研 · 摄入 · 图片 —— 这里才需要更强的 agent |
| 做完了谁看 | 完全空白 | 渲染后反思 |
| 跑得久不久、丢不丢东西 | 现在会丢 | runtime 基础设施 |

**一条贯穿全文的红线：通用化只往 runtime 层加自由度，不往排版层加自由度。**

## 二 · 通用化的四笔隐藏成本

这四条在「域内完整」路线下**都不存在**，是选了通用之后才出现的：

### ① 上下文压缩从「不用做」变成「必须做」

第八轮（R-37）的判断是：续作**不传 history**，
「要接着做的信息全在 deck 里，agent 自己 `getDeck` 就看得到」。
**那个判断在当时是对的** —— 因为 deck 是一个外部状态容器，
它替我们承担了「跨轮记忆」的职责，所以上下文永不累积。

**通用任务没有 deck。** 一个调研任务的中间状态就是它读过的东西本身，
没有任何外部容器可以塞。绕法失效，必须真的做压缩流水线（CC 的做法见 10 号文档 2.4）。

### ② 权限闸门从「可选」变成「必须」

deck 工具的最坏后果是「一页排得难看」，可以撤销、可以重做。
通用工具会碰文件系统、终端、网络 —— **后果不可逆，且在 rabbit 的进程之外**。
BitFun 的 `plan_permission_intents` 那套（含「放行必须窄、拦截可以宽」的不对称匹配）
从参考资料变成前置条件。

### ③ 「一个用户一个任务」的模型撑不住

`orchestrator.ts:427` 的 `activeTasks` 按 `userId` 键 —— 一个用户全局只能跑一个任务。
通用 agent 的常态是长任务在跑、用户同时干别的。这条必须改。

### ④ 差异化优势会被稀释

我们的护城河是**域内深度**：没有第二家把「重叠 / 越界 / 对比度 / 出场顺序」
做成纯几何 lint。往通用走，等于同时在打一场 BitFun（46 crate）和
Claude Code（1902 文件）已经打了很久的仗。

> **保留意见，记录在案。**
> 规划时我建议走「域内完整」（补齐 00-vision 的五层，基础设施学通用的、能力只做域内），
> 理由就是 ④。**决策者选了通用 agent，这是他们的判断，本文按通用 agent 认真做。**
> 记在这里是因为本仓库的规矩是记录分歧而不是抹掉分歧 ——
> 如果半年后证明这条保留意见是错的，这段就是证据；如果证明是对的，
> 回头看会知道成本是在哪一步开始付的。

## 三 · 现在的实际形状

规划时读 `server/src/agent/orchestrator.ts` 得到的四个结构性事实。
**②③④ 已经修掉了**，原文保留 —— 它们是这几轮工作的起点，划掉比删掉有用。

**① 编排是硬编码的直线剧本，不是循环。**（**未修**）
`runAgentTask` 里 if/else 两条写死的路径：Editor 单角色，
或 `Planner → Generator → Reviewer →（可能）Generator 修正`。
角色顺序、次数、prompt 拼接全在那 100 行里。

**这卡死了三类任务**：调研（搜不够要再搜，长度不定）· 深挖单页（要派生子任务）·
并行修多个问题。**剧本表达不了「形状未知」的任务。**

**~~② `activeTasks` 按 `userId` 键~~**（见 §二③）。
→ **A4 已修**：改成按工作区键（`deck:42`），跨 deck 并行、同 deck 串行；
顺带修掉注销的 ABA 竞态（`runtime/taskRegistry.ts`）。

**~~③ `saveDeckState` 只在最后调一次~~**，但 `agent.deck` 每步都实时推画布。
中途失败 → **画布上有改动、库里没有**，刷新就没了。
这比「留半成品」更隐蔽 —— 它是前后端不一致。
→ **B 期第一组已修**：落库与推画布合成一次 `commit`（`runtime/commit.ts`），
每次 mutation 都提交。实测逐次落库 0.19 ms，不需要节流。

**~~④ `cancelAgentTask` 只是 `abort()`~~**，在途的 `agent.deck` / `agent.text` 照发。
→ **B 期第一组已修**：`runtime/cancellation.ts` 的闸门，取消后只放行 `agent.deck`
（它和一次库写入配对，丢掉就是库与画布不一致）。**世代号刻意没做** ——
我们的 send 在调用点同步发，`signal.aborted` 就够；
等接 `cancelAllMatching`（登出 / 断线取消）那条路时再补。

## 四 · 一个刻意的克制：不要把剧本换成自由循环

最直觉的做法是「照 CC 那样改成一个自由的 `while(true)`」。**不要全换。**

剧本的可预测性，正是「把决策挪进代码」在编排层的体现。
换成自由循环 = 把编排决策还给模型 = §一 那条红线要防的事。

正确的做法是**保留剧本，另开一条派生路径**：

```
生成一份 deck（形状已知）      → 走剧本：Planner → Generator → Reviewer
调研 / 深挖 / 自由任务（形状未知） → 走派生：子任务自带工具子集 + prompt + 预算
```

好消息是**原语已经在了**：`runRoleToCompletion` 就是那个东西，
现在只是仅被剧本调用、且写死了 4 个角色。
把它变成「可派生」的改动量，比重写编排小一个数量级。

## 五 · 目标架构

```
server/src/
  runtime/                    ← 域无关。禁止 import domains/
    turn.ts                   单轮循环（State record 写全字段 + transition.reason）
    session.ts                会话 / 回合 / 世代号
    ownership.ts       ⊘      单一权威写者 —— **没建这个文件，见下**
    cancellation.ts    ✅     取消 + 在途事件回收（世代号未做，见下）
    commit.ts          ✅     状态提交：落库与推前端合成一次，顺序即契约
    checkpoint.ts             快照 / 回滚
    permission.ts             权限闸门（纯函数）
    questions.ts              提问注册表（revision 快照 + 生命周期绑定）
    context.ts                上下文压缩流水线
    subagent.ts               子任务派生
    registry.ts               工具注册表（按域分组）
    events.ts                 事件 + 优先级 + 世代
    budget.ts                 ← 现有，加收益递减

  domains/
    deck/                     ← 现有能力原样搬进来，成为第一个域
      kernel.ts   layouts.ts   design.ts   animationOrder.ts   （不动）
      tools.ts    → 注册为 deck 工具组
      events.ts   ✅ 域的取消策略：哪些下行事件在取消后仍必须送达
      channel.ts  ✅ 闸门 + 提交器的接线（域把两个 IO 端点交进去）
      agents.ts   ← roles.ts 改名：4 个角色变成 deck 域的 agent 定义
    research/                 ← 第二个域（阶段 D）
      tools.ts                搜索 / 抓取 / 摄入
```

**`kernel.ts` / `layouts.ts` / `design.ts` 一行不动。**
它们是域内深度，通用化不该碰它们 —— 碰了就是 §二④ 那笔成本提前发生。

> **`ownership.ts` 规划了但没建，理由值得记（第十六轮）。**
> 「单一权威写者」这条能力落地了，但它**落在前端** —— 丢失发生在
> `agentStore.handleMessage` → `slidesStore.setSlides` 这条路径上，
> 权威写者的争夺是「画布 vs agent 推送」，不是两个服务端模块。
> 所以所有权状态在 `src/store/slides.ts` 的 `deckOwner` 上，守卫也在那儿。
>
> 后端本来可以有一个对应的闸门（任务运行时拒绝 `PUT /decks/:id`），
> **也没建** —— `taskRegistry.isBusy()` 已经是那个谓词了，
> 再包一层 `runtime/ownership.ts` 只是给一个 `!` 套壳。
> A4b「没有顺手抽泛型的 runTask 骨架」是同一条理由：**别为想象中的需求建抽象。**
> 等第二个域真的也要抢同一份资源时再抽，那时能看见真正共用的是什么。
>
> **`events.ts` / `channel.ts` 是规划时没预见到的两个文件，理由值得记。**
> 它们本可以写在 `pipeline.ts` 里，但那个文件经 `db/index.ts` 拉进 `bun:sqlite`，
> **在 vitest 里 import 不进来** —— 写在里面等于没有判据。
> 一个装的是**策略**（取消放行哪些事件），一个装的是**接线**（闸门 + 提交器怎么接）。
>
> 后者尤其值得单列：`cancellation.ts` 和 `commit.ts` 各自都有判据，
> 但**「它们被接对了没有」是另一回事**。实测负对照 ⑦⑧ 证明了这一点 ——
> 把 signal 接错、把 publish 改成绕过闸门，两个零件的判据都是全绿的。
> **零件对 ≠ 装配对。**

## 七 · 验收判据（机器能判的）

08 号文档第四节那句「变成机器能判的，才不会退化」在这里同样适用。
拆层这种纯重构最容易「看着像做完了」，所以判据要先立：

| # | 判据 | 怎么判 |
|---|---|---|
| 1 | ✅ **`runtime/` 不得 import `domains/`** | `server/src/runtime/__tests__/boundary.test.ts`（10 条，含真负对照）。抄 BitFun 的 `check:core-boundaries` |
| 2 | **接入 research 域时，`runtime/` 的改动行数为 0** | 阶段 D2 时用 `git diff --stat runtime/` 验。**不为 0 就说明 A 划错了边界** |
| 3 | ✅ **现有 831 个测试不许改，且全绿** | 拆层是搬家不是改行为。要改测试就说明搬出了行为差异 |
| 4 | ✅ **取消后除 `agent.deck` 外 `agent.*` 为 0 条；且任务结束时库里的 `slidesJson` 与最后一条 `agent.deck` 逐字节相等** | `domains/deck/__tests__/channel.test.ts`（10 条，含真负对照）。**这条被改写过，理由见下** |
| 5 | ✅ **任务中途 kill 进程，重启后库里的 deck 与画布一致** | `channel.test.ts` +『每一步之后都成立』· `toolCommit.test.ts` 用真工具走一遍。判据形式是「库里 == 最后一条 `agent.deck`」，而不是两个数各自对 |
| 6 | **`applyLayout` 产物仍然零告警** | `kernel-elements.test.ts` 已有，不许破 |
| 7 | ✅ **每个工具都至少属于一个工具组** | `findUngroupedTools` + `toolGroups.test.ts`。防的是「加了新工具忘了归组 → agent 永远拿不到 → 没有任何东西报错」 |
| 8 | ✅ **角色配额与拆层前逐键等价** | `toolGroups.test.ts` 把拆层前的 23 / 5 个键**独立抄一份**当期望，不从新数据反推 |
| 9 | ✅ **`domains/` 不得依赖装配层** | `boundary.test.ts`。域可以依赖 runtime（地基），反向依赖装配层会让「换一种装配方式」变成要改域的代码 |
| 10 | ✅ **同一工作区同时只有一个任务，且注销不受 ABA 影响** | `taskRegistry.test.ts` 的「ABA 竞态」一组 —— 它就是拆层前那个 bug 的复现脚本 |

> **判据 3 的做法比原文写的更强，记一笔。** 字面上「不许改测试」站不住 ——
> 搬文件必然要改测试里的 import 路径。实际办法是**源文件和它的测试一起搬**：
> 测试用 `from '../kernel'`，两边一起搬之后相对路径原样有效，
> 于是 9 个测试文件**一个字都没改**。这比「只改 import 不改断言」强一档：
> 连改都没改，就没有「改的时候顺手动了断言」的空间。
> 前提是先逐个确认过没有测试跨新边界。
>
> **判据 4 是改写过的，记一笔。**（2026-08-19 第十五轮）
> 原文是「取消后**不再有任何** `agent.*` 消息到达前端」。做「中途落库」时发现
> 它和判据 5 会互相顶：abort 掐的是 LLM 那条 fetch，**工具函数一个都不看 signal**，
> 当前这一步的 mutation 仍会跑完并落库；如果闸门把配套的 `agent.deck` 一起丢掉，
> **画布就比库少一步**，判据 5 立刻破。
>
> 三个方案（前端收到取消回执后重新拉一次 / `agent.deck` 永不回收 / 什么都不补）
> 里决策者选了第二个。新判据断言的是**与库相等**而不是**没有消息**，比原来强；
> 也和 BitFun 一致 —— 它的 `is_reclaimable_stream_data` 回收的是
> `TextChunk` / `ThinkingChunk`，从来不是权威状态。
>
> **教训不在改得对不对，在于判据是什么时候写的。** 这条和判据 3 是同一个毛病：
> 规划阶段凭对系统的想象写下的判据，落地时才发现和别的判据冲突。
> 判据 3 蒙对了，判据 4 没蒙对。
>
> **判据 2 是这份路线里最重要的一条。**
> 拆层的成败不取决于目录长得好不好看，取决于**第二个域接进来时要不要改地基**。
> 这条要等到 D2 才能验，但正因为如此，**A 阶段就要把它写进文档**，
> 免得到时候「顺手改两行 runtime」把唯一的判据消解掉。
